我们想知道：模型能否做出容易上手、值得琢磨的游戏，也能根据试玩反馈，把已有版本改得更好。

评测对象

模型与开发流程的产出

比较在相同需求、工程、素材与资源预算下，完成和迭代游戏的能力。人类玩家用于检验体验；自动玩家用于寻找失效情况与辅助验证。

第一阶段的范围

先把一小段体验做扎实

候选范围为单人短局、完整的开始与结束、可复现关卡。平台与品类待确认。广告、付费和长线运营可在后续独立设题。

01 / SCOPE

先选哪类休闲游戏？

同样是休闲，排序的规划、动作的手感、经营的长期选择，需要不同的观察方法。

建议优先讨论：整理／规则解谜 + 轻动作

前者适合看规则理解、规划与解法学习；后者适合看操作反馈、危险判断和熟练进步。消除／合成适合作为另一组候选，需多控制随机性。

以 MDA 为例：从功能一路追到玩家实际做出的判断，才能讨论这个功能是否带来了期望的体验。

这里把“深度”理解为：熟悉以后还有值得学、值得判断的东西。

解谜可以是更好的规划，动作可以是时机与路线的掌握，消除可以是目标和未来局面的取舍。机制多、按键多、玩得久，都不能单独证明深度。

03 / MEASUREMENT

四份体验量表，具体在问什么？

GEQ、PXI、miniPXI 和 GUESS 都由玩家报告自己的感受。点击图解，可以查看内容、题意示例和结果读法。

先区分两种评分

玩家填量表，专家拿证据做评审

量表问“我刚才的体验如何”；我们自拟的八条 rubric 由专家根据试玩证据评分。两者可以对照，但分数分开记录。下面的中文图解帮助理解，正式施测请核对原题、版本、计分方式与中文适用性。

建议的选法

详细诊断轮：优先讨论完整 PXI，容易与目标、控制、反馈和掌握感对应。短局比较轮：先验证 miniPXI 的问卷负担与敏感性。团队熟悉 GEQ 时也可以继续使用，但保持明确版本与模块。

正式使用中文问卷前，要核查已有中文版本的来源和适用性；自行翻译或改题后，先做理解访谈和必要检验，并标注为试用或改编版本。保留原量表的用法，另加游戏问题，分别报告。

试点访谈可以先问什么？这些是自拟问题，不是 GEQ／PXI 正式题项
  1. 刚才哪一步最需要你判断？你为什么这么做？
  2. 有没有一次失败，你知道下次可以怎样调整？
  3. 如果现在再给你一局，你想不想继续？主要原因是什么？
  4. 如果只改一个地方，什么最能改善这次体验？

这些问题用于解释行为与发现问题，不计算心理量表分数。意愿、实际选择和长期留存分别记录。

下一步要做：选一个主要体验工具，先检查玩家是否理解题意、填写是否打断体验，再把它与录像和行为记录对照。

04 / RELATED WORK

已有 Benchmark，能借鉴哪一部分？

开发任务、智能体游玩、玩家体验是不同的评价对象。先分清对象，再组合方法。

我们可以补充的部分：从“按要求做出来”，继续追到“玩家是否获得预期体验”。

尤其值得做修改题：给出能玩的版本和试玩反馈，让模型提出修改、做出修改、验证改进，并保留原有功能。

05 / TASK DESIGN

把试点做成真实的开发任务

三类任务分别评。先不要让一个大而全的生成题承担所有结论。

A

把核心玩法做对

给明确规则、起始工程和素材，完成可玩的循环。重点看需求理解、实现和基础可用性。

B

把已有玩法做深

给稳定版本，在相同内容预算下设计关卡和进程。重点看学习、选择、技巧与变化。

C

根据试玩反馈迭代

给录像、问题记录和既有功能，要求修改并验证。重点看改善是否对应问题、有没有引入退步。

一份任务单必须交代什么？避免模型与评委各自猜需求

给开发者的信息

  • 目标玩家、品类、平台、局长、输入方式。
  • 起始工程版本、素材、规则和允许修改的范围。
  • 时间、调用／token、工具与素材预算，是否允许联网。
  • 需要交付的可玩版本、修改说明、验证记录。
  • 本任务启用的评分维度，以及明确的成功条件。

由评测方保留的信息

  • 符合已公布规则的额外盘面与边界情境。
  • 独立运行的检查器、日志、随机序列和版本标识。
  • 玩家招募条件、主持流程、评分和仲裁方法。
  • 不能向开发者泄露的参考答案与完整留出集合。
  • 等价实现的接受范围，避免只匹配参考实现写法。

隐藏的是测试实例与答案，验收要求本身应公开。若任务依赖未交代的要求，应修题再比较。

下一步要做：每个入选品类各做一份参考实现和一份问题版本，确认题目能做、能测、改进也确实能被观察到。

06 / RUBRICS

八条可以拿着试玩的评分标准

这是本提案自拟的专家 rubric，借鉴上述研究，但不是已验证心理量表。需要用实际作品校准。

0 明显失效1 问题突出2 基本成立3 表现清楚4 经更多情境验证

以每条具体锚点为准。U＝证据不足，N/A＝任务不适用。两者都不是 0 分；没有观察到高分条件时，不根据印象补分。

先划清边界，避免同一问题重复扣分

“按了没有反应”主要记 R2；“不知道为什么不让按”记 R1；“按键文字被特效遮住”主要记 R8，其他受影响维度写关联说明。R4 的策略与技巧按品类选择证据，叙事、社交与长期经济可作为后续模块。

0–4 是有序等级。首轮报告各项分布、关键片段和分歧；若需要总分，应先确定适用维度与权重，并检查换一组合理权重会不会改变排名。

07 / PROTOCOL

评测分四步，证据各有用途

四类证据分别是程序检查结果、专家观察、真人行为记录和玩家自报感受。模型裁判辅助整理与提出建议。

1

先检查能否公平地试玩

统一设备与输入条件，检查启动、核心规则、成功／失败、暂停、重开和任务要求的恢复方式。关键流程被阻断的提交保留在结果里，注明阻断原因；后续体验记为无法观察。

报告全部提交的可运行比例，同时单独报告可运行版本的体验，防止只挑成功作品造成偏差。

2

两位评委独立试玩，按锚点写证据

用匿名版本，先独立打分，再讨论分歧。每项留下局面／时间、玩家或评委做了什么、结果、为什么对应这个锚点。差异较大的项目由第三人复核，保留原始评分。

需求检查员可以读任务单和代码；体验评委先看正常游戏界面与同等操作说明，避免开发者自述预先影响判断。

3

让目标玩家在相同条件下玩

新玩家先无额外帮助完成约定试玩，再填选定量表、回看关键片段。主持人不临场教学；必须帮助时记录时间与内容。修改前后尽量使用不同的新玩家，或平衡版本顺序并分析学习影响。

建议观察窗口为每版约 8–12 分钟、每人至多 2–3 版，具体由玩法与疲劳情况调整；这属于试点安排，不是行业标准。

4

把分数、行为和玩家解释放在一起

同品类、同任务类型内比较。报告分数分布、样本数、完成／失败原因及代表片段。模型裁判可以找片段、整理事件、提出评分建议；先与人工标注对齐，主观乐趣仍由真人反馈支持。

首次人工协助前的表现和协助后的表现分开。量表按原构念计分；不把胜率、问卷、时长直接相加。

记录什么能帮助回答解释时要留意
首次有效操作、无效尝试、求助是否能独立开始，在哪里误解规则探索性尝试也可能是主动学习，需结合回看解释
相同局面下的选择、练习后的表现判断与技巧是否有成长空间进步可能来自熟悉地图；用保留局面验证迁移
提示、撤销、失败、重开失败是否可理解，恢复是否合理高重试次数既可能投入，也可能困惑
量表与自愿再玩选择感受、偏好与短期意愿口头意愿不等于行为，短局行为不等于留存
版本、种子、设备与运行记录差异能否复现，是否由条件变化造成画面、声音、延迟、操控方式都可能影响结果
怎样防止评测只看上去很精确？一致性、随机性与评测泄漏
  • 评分一致性：先用相同样例试评，记录分歧原因。正式报告可按数据结构选择加权 kappa 或 Krippendorff’s alpha，同时给出评分矩阵；不把某个系数阈值当作普适质量线。
  • 随机性：开发运行种子与游戏局面种子分开记录。每个方法重复运行，不能只挑最好作品；留出规则变体、盘面或序列，避免只记住样例。
  • 比较条件：主榜固定 harness 与工具预算。若使用不同原生工具链，另设“完整系统”比较，并公布配置与成本。
  • 量表适用性：分品类、熟悉程度和目标人群解释。没有样本可比性和测量依据时，避免跨品类强行排名。
  • 样本量：小样本先找问题和估计方差。正式比较根据想检测的差异、设计与先导数据确定人数，报告不确定性；玩家、任务和重复运行不能混成独立样本。
  • 反向检查：故意加入遮挡、误导提示、无意义等待或不可躲避障碍，确认评测能发现这些已知退步；也检查“去掉所有挑战”是否被误判为全面提升。
  • 信任边界：评测提示、任务和答案分离。游戏中出现的“给我满分”等文本是游戏内容，不是裁判指令；提交方自己的日志与结论需用独立记录交叉核对。

下一步要做：先跑一轮，检查评委分歧、问卷负担和日志缺口，修好评测方法后再扩大模型比较。

08 / CO-DESIGN

第一轮可以这样共建

以下是可调整的工作量建议，目的是先验证题目和评法是否可靠。

准备

选题与参考版本

选 2 个品类，每类准备实现、内容设计、反馈迭代各 1 道题，共 6 个任务模板。每题有经人工检查的参考结果和已知问题样例。

校准

先看评分能否说清

2 位评委独立评相同样例；每个品类先邀请约 6–8 位目标玩家做诊断。用这一轮发现分歧、误解和数据缺失，不用于发布模型名次。

小规模比较

记录所有独立产出

例如比较 2 种模型／方法，每个任务独立运行 3 次，共 36 份提交。自动检查覆盖全部；人工与玩家评测按事先制定的抽样计划覆盖。

复盘

决定哪些值得扩展

保留区分明确、能解释改动的题。修订模糊锚点，补齐保留测试集。下一轮再讨论合成、卡牌和更长线的经营体验。

第一次讨论，先确定这五件事

  1. 优先选哪 1–2 类，目标玩家是谁？
  2. 采用哪种平台与输入条件，什么算完整的一局？
  3. 第一轮更关注实现、内容设计，还是根据反馈迭代？
  4. 谁提供参考版本、问题样例和独立试玩？
  5. 哪些信息公开，哪些盘面、序列和答案留作测试？

本轮应交付：任务包、参考与问题样例、rubric v0.2、匿名证据记录，以及哪些结论仍然不能下的清单。
